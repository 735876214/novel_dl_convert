## 冒烟抓出的真缺陷（已修 + 已钉测试）

**自定义面板「库范围」受控 checkbox 停在不存在的中间态**：勾一个库 ⇒ 标题「1 个书库」；再点取消 ⇒
标题**仍**是「1 个书库」但界面上已显示未勾选；再点一下 ⇒ 变成**选中**（方向反了）。
根因：`input` 用 `:checked` 绑定 + `@change`，而「取消最后一个勾选」**故意不改 store**（拒绝并 toast）
⇒ Vue 不重渲染 ⇒ 浏览器翻过去的原生勾选态留在原地。
**修复** = 拒绝分支里回写 `(ev.target as HTMLInputElement).checked = true`（`toggleLibraryScope` 改为收事件对象）。
**为什么常规验证测不到**：原有 43 个 spec 从没打开过面板库范围区；端到端只看 JSON 与产物字符串。
⇒ 新增 `DashboardSettingsSheet.spec.ts`（5 例，含「拒绝时 DOM 勾选态必须与 store 一致」这条关键断言）、
并登记进 `EXPECTED_SPECS`。**已用「临时移除修复 → 该例变红」验证过测试真的抓得住**。

# 同日第九件事 · 环境排障：IDE「AI 服务调用失败（self signed certificate）」→ 已按首选处理

**报错**：`Error Code 10006` / `Cannot connect to API: self signed certificate; ... try running Node.js with --use-system-ca`（11:10:30 那次中断）。

**定位（只读检查结论）**：
- 系统级代理 `ProxyEnable=1 / 127.0.0.1:7897`，7897 进程 = **`verge-mihomo`（Clash Verge）**；8080 是 steamwebhelper（无关）；`%WINDIR%\...\hosts` 无异常行。
- 系统根证书里有一张本机自建根 CA：**`CN=Yaya的小电脑`**（`LocalMachine\Root` + `CurrentUser\Root`，**带私钥**，NotBefore 2026-09-30 09:49、NotAfter 3026，有 EKU 无 BasicConstraints），指纹 `5C71BAB8D5148E7485A6605E72D81F1AC072D9AE`。⇒ Node 默认只信内置 Mozilla CA 列表（121 张），不含它 ⇒ `self signed certificate`。
- `--use-system-ca` **可放进 `NODE_OPTIONS`**（实测 `node` 接受，exit 0）；本机 Node 是**系统级安装** `C:\Program Files\nodejs`（v24.21.0），**无多版本 nvm** ⇒ 设全局 flag 不会被旧 Node 顶成「bad option」。

**已执行（首选方案）**：
```powershell
[Environment]::SetEnvironmentVariable('NODE_OPTIONS','--use-system-ca','User')   # 原值为空，已写入
```
**机制验证**：Node 默认信任集 **121 → 210**（并入系统库 89 张）；按 SHA-1 指纹比对，`CN=Yaya的小电脑` **确实在这 210 张里**（`getCACertificates('system')` 含 Yaya = true）。
**端到端复测**：公共站点复现不出（多被 mihomo 重置）；`openrouter.ai`（`~/.codebuddy/models.json` 指向它）加 flag 后报错从 `ECONNRESET` 变成 **`ERR_TLS_CERT_ALTNAME_INVALID`** ⇒ **信任链已通过**，剩余是代理侧证书缺 DNS SAN。
**生效条件**：环境变量在**进程启动时**读取 ⇒ **必须完全重启 IDE**（关掉所有窗口/扩展宿主）后重试。
**回滚**：`[Environment]::SetEnvironmentVariable('NODE_OPTIONS',$null,'User')`。
⚠️ **安全提示**：那张根 CA 私钥在本机，且被 Windows 信任 ⇒ 它能签发任意站点证书（HTTPS 可被解密）。若并非本人有意安装（如某工具的「HTTPS 解密」功能），建议查明来源后决定是否移除；`--use-system-ca` 等于把这个信任也带给了 Node。

3. **全部验证串行 + 1.5s 间隔，且间隔只在两条之间睡**（最后一条后面不睡，否则每次全验
   白等一个间隔）。`manager.test_source` **自身没有单源超时**，`probe` 里必须自己包

### ⚠️⚠️ 真机跑出一个离线桩永远抓不到的 bug（务必记住）

`subprocess.run(..., text=True)` **没指定 `encoding`** ⇒ 用系统区域编码（Windows 是 GBK）
⇒ Node 输出的**中文**撞 `UnicodeDecodeError`，而异常发生在 subprocess 的**读线程**里
⇒ `proc.stdout` 变成 `None` ⇒ 用户看到的是
`AttributeError: 'NoneType' object has no attribute 'strip'`，离真正原因十万八千里。
**修法：显式 `encoding="utf-8", errors="replace"`，并把 stdout/stderr 都按 None 兜底。**
👉 教训：**凡是调子进程，一律显式指定编码**（本项目其它 `subprocess.run` 调用点也该排查一遍）。

## ✅ Node 解密通道**接进内容链路**（第 5 步主项收尾）

- `network.wrap_decrypt(js)`：把「Legado 风格、用 `return` 交出明文」的片段包成
  `const __out = (function () { … })();` 再打印一行 JSON `{ok, v}`。
  ⚠️ **这层包装不是装饰**：`run_js_sync` 是把片段拼在**脚本顶层**的，而 `return` 在顶层是
  **语法错误** ⇒ 不包就得到 `SyntaxError: Illegal return statement`，看起来像「这条规则写错了」，
  实际是**我们的调用方式**错了（`SourceAdapter.decryption_js` 的契约写明是 `return`）。
- `network.run_decrypt(js, text)`：`__args[0]` 传密文；结果**必须是字符串**，
  `undefined` / 对象一律如实抛错（静默当明文返回 ⇒ 书里写进一段 `undefined`，用户只看到「内容乱了」）。
- `RuleBasedSource.decryption_js()` 读规则里的 `decrypt_js`；`_decrypt(text)` 没配就**原样返回**

# 同日第十五件事 · 用户报缺陷「漫画库：删库后重新添加同一文件夹读不到内容」

## 已修的（**确定**的一处，`catalog.forget`）

`catalog.forget(lid)` 过去只清 `book_index` 行 + 内存标记 + Redis 键，**没清
`app_state['book_index_rule:{lid}']`**。而库 id 由**库名**派生（`server._new_library_id`：
ASCII 名 slug / 中文名 `lib-<sha1[:8]>`）⇒ **「同名重建」会复用同一个 id**，
新库一上来就带着旧库的口径标记，被 `_rule_stale` 判为「口径已是最新」而**跳过全量重扫**。
已在 `forget` 里补 `db.state_delete(_rule_key(lid))`（try/except 包住：清残留失败不该让删库失败）。
测试 `tests/test_catalog_forget_cleanup.py` 2 例。

## ⚠️ 但**很可能不是空书架的根因**（已排除的方向 + 待确认的机制）

用子代理普查（93 次工具调用）后的结论：

**已排除**：
- ❌「路径去重把重建挡死」—— 建库只按 **id** 查重（`server.py:4523`），没有 source_dirs 重复拦截；
- ❌「旧 `book_index` 残留行挡掉新库」—— 删库确实清行（`catalog.py:502`），且读也是

  残留行只会**帮它显示**而不是挡它。

**两根因的裁决（用户确认：「本地原件还在原位置」）**：

# 同日第十六件事 · 第 6 步 `update-append` 开工（先落最底层、可自证的一块）

## 已落：`core/epub_update.py` 的 zip 转发原语（`copy_with_extra` / `verify_unchanged`）

**为什么先从它开始**：追更的硬约束是「**既有条目一字不动**」（进度/批注/书签/会话全按
`(book_id, 条目 index)` 记录），而这条约束**最容易被一个环节悄悄破坏**。
所以先把它做成**可执行判据**，后面重写 OPF/nav、接入 `manager.update` 才有地基。

- `copy_with_extra(src, dst, extra=[…], replace={…})`：**按原顺序**复制既有条目
  （沿用 `compress_type` / `date_time` / `external_attr`），`extra` 追加在末尾，
  `replace` 就地替换（重写 OPF / nav 用）；**原子写**（`.part` + `Path.replace`，
  与「源不可变、副本禁原地写」同一条纪律）；`mimetype` 仍居首且 `ZIP_STORED`。
- `verify_unchanged(src, dst, added=…, replaced=…)`：逐条核对顺序 / 内容字节 /
  `compress_type` / `date_time`，返回**违规清单**。**「我做的是增量追加」从此是断言，不是承诺。**
- ⚠️ 「字节不变」的口径说清：保持**解压后的内容字节**与元数据；重新压缩出的 deflate 流
  不保证逐位相同（那由 zlib 版本决定，不是能承诺的东西），但阅读器与阅读数据看到的
  条目内容与顺序完全一致。

测试 `tests/test_epub_update.py` 6 例（**用真 EPUB 夹具**）：一字不动（含顺序）、mimetype 居首不压缩、
就地替换 OPF、原子写不留 `.part` 且不动源文件、深层目录也能写、**校验本身能抓出内容漂移**
（否则那条判据就是摆设）。

## ⚠️ 本轮踩的两个小坑（都是编译检查/测试当场抓到的）

## ✅ 章节级 API 的**结构基线**（真机取出来的事实，下次直接照它写，不要再猜）

`epub_builder.build_epub` 用的是 **ebooklib**（`epub.write_epub`）—— 所以产物结构是 ebooklib 的。
真机 dump（`build_epub` 两章）：

```
ENTRIES: mimetype, META-INF/container.xml, EPUB/content.opf,
         EPUB/c0000.xhtml, EPUB/c0001.xhtml, EPUB/toc.ncx, EPUB/nav.xhtml
OPF:     EPUB/content.opf
manifest: <item href="c0000.xhtml" id="chapter_0" media-type="application/xhtml+xml"/>
          <item href="c0001.xhtml" id="chapter_1" media-type="application/xhtml+xml"/>
          <item href="toc.ncx" id="ncx" media-type="application/x-dtbncx+xml"/>
          <item href="nav.xhtml" id="nav" media-type="application/xhtml+xml" properties="nav"/>
spine:   <spine toc="ncx"> <itemref idref="nav"/> <itemref idref="chapter_0"/> <itemref idref="chapter_1"/> </spine>
NCX:     EPUB/toc.ncx（`<navMap>` 里逐条 `<navPoint>`）；nav.xhtml 紧随其后
```

**由此定下章节级 API 的做法**（⚠️ 计划明令**不走**「ebooklib 重建」那条路 —— 那会把
「字节不变」变成「希望一致」）：

1. 新章条目名 `EPUB/c%04d.xhtml`（4 位补零）、manifest id `chapter_%d`（**不补零，0 基**）
   ⇒ 追加第 N 章（N 从 0 起）= 文件名 `EPUB/c000N.xhtml`、id `chapter_N`；
2. 三处 XML 用 `replace=` **就地重写**（其余条目由 `copy_with_extra` 原样搬运）：
   · OPF：manifest 里加 `<item href="c000N.xhtml" id="chapter_N" media-type="application/xhtml+xml"/>`
     （插在 `<item href="toc.ncx"` 之前最省事）；spine 里在 `</spine>` 前加 `<itemref idref="chapter_N"/>`
     （既有章节顺序不变 ⇒ 阅读数据的 index 不漂移）；
   · `EPUB/nav.xhtml`：在目录 `<ol>` 末尾加 `<li><a href="c000N.xhtml">标题</a></li>`；
   · `EPUB/toc.ncx`：`<navMap>` 末尾加 `<navPoint id="chapter_N" playOrder="…">` + `<navLabel><text>标题</text></navLabel>`
     + `<content src="c000N.xhtml"/>`；
3. 新章的 XHTML：**照既有章条目的字节风格生成**（下次可先 dump 一个 `EPUB/c0000.xhtml` 的前 200 字节，
   头部/命名空间/编码与它保持一致），不要自创模板 —— 同书内两种模板会被某些阅读器区别对待。

⚠️ 既有条目的 `nav.xhtml` / `toc.ncx` / `content.opf` **本来就属于「replaced」**（重写是必然的），
`verify_unchanged(..., replaced={这三个})` 正好用来证明「除了这三处 + 新章，其余一字不动」。

## ✅ 三处 XML 登记点已落地（纯函数，`tests/test_epub_update_xml.py` 4 例）

`epub_update` 新增四个纯函数（**落点全部由真机 dump 决定，不靠记忆**）：

- `add_manifest_item(opf, href=…, item_id=…)` → 在 `</manifest>` 前插 `<item …>`
- `add_spine_itemref(opf, item_id=…)` → 在 `</spine>` 前插 `<itemref/>`（**末尾** ⇒ 既有章节
  顺序不变 ⇒ 阅读数据 index 不漂移）
- `add_nav_link(nav, href=…, title=…)` → 在 `</ol>` 前插 `<li><a …>`
- `add_ncx_navpoint(ncx, href=…, title=…, play_order=…)` → 在 `</navMap>` 前插 `<navPoint>`

共用 `_insert_before(..., what=…)`：**锚点找不到就响亮报错** —— 「静默无动作」在这里是最坏的
失败形态（条目照样追加、包照样生成、一切看着都成功，只是读者翻不到新章）。

测试四例：**先钉三个锚点在真产物里确实存在**（锚点猜错的话后三个函数的测试会「全过」而实际
什么都没插）、三处插完仍是合法 XML 且 spine 顺序正确、锚点缺失时响亮报错、

### ⚠️ `tests/test_updater.py` 在全量运行里偶发失败（**未修**，已收敛到一条嫌疑）

四次全量运行里，**同一文件里三条不同用例**各失败过一次：

| 运行 | 失败用例（实际值都是 `'no_update'`） |
|---|---|
| 1 | `test_maybe_auto_apply_换版本清零失败计数`：`assert 'no_update' == 'restarting'` |
| 2 | 无（全绿） |
| 3 | `test_maybe_auto_apply_退避序列封顶24h` |
| 4 | `test_maybe_auto_apply_首次自动拉取并记录已尝试`：`assert 'no_update' == 'already_tried'` |

**已排除的假设**（都做过实验，别再重复走）：

- ❌「真去出网查版本」—— `test_updater.py` 的 `up` 夹具**早已**把 `updater._http_get_json`
  换成替身（`net.get`），不出网；
- ❌「新增测试文件触发」—— 与 `test_audio_ingest` / `test_comic_ingest` 组合跑 **38/38 过**；
- ❌「后台线程没停、跑到下一个用例里改写 `_state`」—— 本轮在夹具 teardown 加了
  `assert t is None or not t.is_alive()` 护栏，**四次运行里护栏一次都没触发**（线程是停住的）。

**✅ 已修（第 86 期收尾）——真因与修法**

**真因**：`updater._state` 是**模块级全局**，而 `server` 的 lifespan 启动时会
`updater.start_background()`（`_apply_update_config`）⇒ **别的用了 `client` 夹具的用例会留下一个
真的在跑的检查线程**。本机可出网，它**真去查 GitHub**，并把结果写进 `_state` 与 DB ——
于是 updater 自己的用例读到的是「别家线程刚写下的」状态，而那种状态恰好是「空 / 无更新」。
这解释全部现象：**每次失败的用例都不同、实际值恒为空/None、单跑整个文件全过**。

**两处修法**：
1. `tests/test_updater.py` 的 autouse 夹具在**用例前后都** `updater.stop_background()` + `join(5)`
   （之前只在**收尾**停 —— 尾随的别家线程会在本用例**开始之后**才动手，所以挡不住）；
2. **产品侧语义修正**：`maybe_auto_apply` 把 `already_tried` 判到 `no_update` **之前**
   （判据带 `latest and` 守卫，免得 `"" == ""` 被当成「已试过」）。原因：一次**成功**的自动更新
   会**合法地**把 `has_update` 清掉，原顺序会把「同一版本已经换过了」误报成「没有新版本」——
   这个顺序缺陷对用户是实打实的（界面会显示「已是最新」而不是「已尝试过该版本」）。

**验证**：连跑 **3 次全量全绿**（1491 例 / 0 failed / 0 errors / 12 skipped）；改动前 7 次里失败 5 次。

👉 **纪律**：遇到「跨用例偶发 + 实际值恒为空/None」，优先怀疑**共享的模块级全局**被
**别家用例起的后台线程**改写；测试夹具要**前后都**停线程，只在收尾停挡不住尾随线程。

### 三类产物接进下载路由（本轮）

- `server._product_kind(name)`：判据**在规则里**（`book.mode`）—— 书源自报产物类型，
  不让用户选、也不靠猜；认不出来（含内置适配器：磁盘上没有规则文件）一律按 `text`，
  既有行为一字不变。
- `server._dispatch_product(mgr, kind, item, root, opts)`：`text → download_to` /
  `comic → download_comic` / `audio → download_audio`；认不出的类型**按文本走**（绝不静默空转）。
- `_KIND_PROBE_NAME`：交给 `resolve_target` 判库的**代表文件名**（`.epub` / `.cbz` / `.mp3`）。
  ⚠️ 音频产物是**目录**，但判库按扩展名 ⇒ 传目录名会让「只收音频的库」认不出来，
  那本书只能报「没有可接收的书库」。
