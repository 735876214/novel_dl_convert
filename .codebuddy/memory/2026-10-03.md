# 2026-10-03 · 第 88 期：书库加载慢（touching 后端请求路径 + 前端感知）

> 需求原话：「我刚将电子书导入书库，但在书库中显示加载等待时间过长。请分析可能导致延迟的原因，
> 并提出优化方案以缩短显示时间。请考虑书库数据量、索引机制、加载策略及界面反馈等因素。」

## 现场口径（用户确认，后续按此判断）

- 部署 = **docker-compose 默认（Redis + PG 都在）** ⇒ 封面/列表缓存正常，**`③封面链`基本可排除**；
  主犯是 **`②刷新跑在请求线程里`**。
- 症状三条全中：**每次打开书库都慢** / **导入后第一次特别慢** / **显示「这个书架还是空的」很久才有书**。
- 范围由用户拍定：**全量**（含分页与虚拟滚动）。

## 摸底结论（两路只读子代理，行号为当时 HEAD）

**后端**：`GET /api/books`（`server.py:1672` → `library.books()` → `catalog.books()/books_of()`）
稳态是快的（读索引、DB 查询全批量无 N+1、有 gzip，600 本实测 65–73ms，`docs/TODO.md:200`）。
真问题两处：
1. **`catalog._settle`（`catalog.py:643-658`）在请求线程里同步跑 `refresh_library`**
   （整目录遍历 + 每文件一次 stat，必要时逐本 probe）。触发：冷启动 / 库被标脏 / 口径版本变化。
   NAS 上每次 syscall 毫秒级 ⇒ 266 本即数十秒。这正是第 62 期「书架 42 秒」的同一处。
2. **`/convert` 与 `/convert-path` 入库后不调 `library.invalidate()`**（其它写路径都调）
   ⇒ 新书只能等 watcher 全量兜底（默认 60s）。**确定性缺陷**。

**前端**：`ShelfView.vue` 加载期**完全没有反馈**，`library.loading` 从未被视图使用，
`sorted.length===0` 直接落进 `EmptyState`（「这个书架还是空的」）⇒ **数据在路上却告诉用户没有书**；
另外 `loadBooks` 把 `/api/books` 串在两个 `/api/reading-thresholds` 之后（白多一个 RTT）；
全量 `v-for` 无虚拟化；每卡一个封面请求；`request()` 无超时无重试。

### ⚠️ 契约变更（要记住，这是有意的）

`library.invalidate()` 之后**下一次读**：由「**同步**增量刷（必然是新数据）」改成
「**派后台刷新 + 最多等 `SETTLE_WAIT`(0.25s)**，到点如实返回现有索引」。
- 为什么：前者正是「每次打开书库都慢」的根因（NAS 上整目录 stat 挂在请求上）。
- 代价：**可能短暂显示稍旧数据**；可见性改由前端轮询补（`scanning` + `scan-state`，扫完自动重取）。
- 想「一刻不等」：把 `catalog.SETTLE_WAIT` 置 0，**但必须同时**把「写后立刻读」那批用例改成轮询语义。
- 既有测试 `tests/test_catalog.py::test_标脏后的读会看到新书` 已按此**改写并说明理由**
  （并特意警告不要写竞态断言：后台可能抢在本次读之前写完）。

## ⚠️⚠️ 事故：子代理「被取消」并不等于「已停止」

第一次派的后端子代理，我的工具调用因 idle 超时被取消，**但它的进程继续跑**，
并与我随后派的第二个后端代理**并发编辑同一个工作区**（第二路自己发现了：文件在它未调用任何工具时仍在变，
`tests/test_catalog.py` 在 01:05 被前者改写、`tests/test_scan_background.py` 在 01:16 由前者新建）。
后果：我第一次跑全量看到 56 red（当时语义已改、契约测试还没跟上），据此 stash 回滚；
而第一路后来把契约测试也改了，于是第二路接手时的树已不是我 stash 前的样子。

**纪律（下次照此做）**：
1. 子代理超时被取消后，**不要立刻假设它停了** —— 先 `git status` + 看文件 mtime，确认工作区静止再动手。
2. **一个工作区同一时间只派一个会写代码的子代理**（要并行就分开目录/用 worktree）。
3. 给子代理的规格里必须写明：**不许改既有测试**；若断言与目标冲突，**停下来报告**，不许自作主张。
4. 子代理会在仓库根留下临时文件（本轮 `_run_pytest.bat` / `junit.xml` / `pytest_out.txt` / `cat_out.txt` /
   `_parse_junit.py` / `pytest_*.txt`）⇒ **提交前先清根目录**（本轮已清）。
5. 子代理报告里「我没做 X」比「我做了 Y」更值得读 —— 本轮正是靠它交出了第 1、2 条冲突才没酿成更大的错。
