### A. 书签（`bookmark-core` / `bookmark-ui`，已提交推送）

- **`bookmarks` 表**：`UNIQUE(book_id, anchor)` + 软删除（`deleted_at`），语义与批注同构。
  两处只属于书签的口径：**位置去重**（同 anchor 恒一行）与 **tombstone 复活**（同位置再加是复活
  那一行、保住 `created_at`，不是插新行）。
- **并发合并 = 乐观并发**：客户端回传它看到的 `updated_at`（不是自己的当前时间，比较只用服务端时钟），
  库里更新则 `applied=False`、**不改库**并把现值回给客户端；墓碑比快照新时不复活。

  `_remap_bookmarks()` **逐行搬 + 撞墓碑时先弃墓碑**（走到那里时目标 id 必无活跃行，冲突方只可能是墓碑）。
  教训：**给既有表加唯一约束时，必须回头看 `remap_book_id` 这条搬迁路径**。

### E. flaky 两条真根因（`db84bb5`、`a26147c`）

- **① 刮削 worker 停机后仍会落库** → `scrape._epoch` 世代号（`stop()`/`start()` 推进世代；各落库点校验，
  作废即 `aborted` 不写库）。确定性复现：替身把「一条要跑很久」变成事实 + 显式演夹具的换库动作
  （⚠️ 必须**改 `DATA_DIR`** 再 `close+init`，否则重开同一文件、断言失去意义）。
  对照实验：临时把 `_stale` 改恒 `False` ⇒ **恰好**两个断言守卫的用例红、第三个照旧绿。
- **② 随机 UUID 被当成 ISBN**（≈1/3 命中）→ 形状判定收敛到唯一真值源 `metadata.isbn_digits`
  （`library._isbn_of` 与 `fileops._set_isbn` 都调它；后者原先会把书**自己的标识符覆盖掉**）。
  定位靠「逐层打印」：每本书的 `audit(b)["score"]/present` → 锁定 ISBN 那 10 分 → 再打印
  `dc:identifier` 与 `_isbn_of` 看到随机 UUID。探针：修复前 6 轮漂 2、修复后 8 轮恒 32.0。

### D. win32「flaky」的真相（`16b0fb1`、`92c8c48`）

**一例是产品 bug、两例未复现。** 第一例 `test_audiobook_library_scan_triggers_auto_fetch` 长期稳定失败，
根因＝`handle_file` 用 `p.stat().st_size == 0` 判空文件，而 **Windows 上目录 `st_size` 恒为 0**
⇒ 音频目录在到达 `p.is_dir()` 分支前就被跳过 ⇒ **win32 上有声书永远不入库**（Linux 目录 st_size 非 0，CI 永不暴露）。
定位难点：报错只有 `calls == []`，完全不指向根因；**「长期稳定失败」本身就是线索 —— 真 flaky 不会次次都挂**。
第二/三例 4 轮全量未复现，机制已写进文档（残留 worker 取到 `isolated` 换过的**新库** ⇒ 全局 `total` 断言落空）；
**按拍板不改测试逻辑、不动 `total` 口径**。
