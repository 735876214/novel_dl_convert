### D. 观察项 3：`InterfaceError` 的真相（与计划假设**不同**）

计划里的 H1 是「写线程持锁 `commit()` 会重置该连接上的所有语句 ⇒ 另一线程中途 `fetchone()` 抛
`InterfaceError`」。**被直接实验证伪**：`executescript`/`rollback`/`commit` 三种操作各自与一个整窗口
持有游标的读线程对撞 2 秒 —— **全是 0 异常**。而常见的 sqlite3 误用（cursor 关后用、连接关后用、
参数错、`row_factory` 非 callable …）产出的都是 `ProgrammingError`/`TypeError`，**没有一种能造出
`InterfaceError`**。（该消息本身不在 `_sqlite3.pyd` 里 —— 是 SQLite C 库 `sqlite3_errmsg` 的
`SQLITE_MISUSE` 默认描述；去二进制里 `strings` 会扑空，实测偏移 -1。）

**真机制 = 同一连接上的无锁并发访问，且不需要 `close()` 就能造出来**：

| 探针（放大版） | 修复前 | 修复后 |
| --- | --- | --- |
| 3 线程裸读 `get_library` + 1 线程锁内 `create_library`（4s） | **3/3 轮全 `InterfaceError`**，各 400–500 次 | **0**（3/3） |
| 同上 + 读该库生效设置（= 用户可见症状） | **1973/2303/2509 次每 5s**，另加写失败 269/298/254 次 | **未发生** |
| 3 线程裸读 + `db.close()`（4s） | **6/6 段错误**（exit 139） | **exit 0** |

**生产可达**：`create_library`/`update_library` 持锁写而 `get_library` 裸读，生产里 watcher 线程、
scrape worker、`server.py` 的 `asyncio.to_thread(migrate.execute)` 与请求线程都会同时进这个连接。
**用户可见后果不是「报个错」**——`library.get_library` 把异常吞成 `None` ⇒ `lib_settings.overrides()`
得空 dict ⇒ **每库覆写静默回落全局值**：用户关掉某库「自动刮削」，读回来又是开的。

**它还闭合了第 38 期 F 小节那条偶发**：`test_scrape_publish.py` 断言 `auto_enabled is False` 却拿到
`True` —— 刚设完 `scrape.enabled: False`，读回时撞上并发写，覆写被吃、回落成全局 `True`。**逐字吻合，
两件事同一个根因。**

**修法**（用户拍板的单点代理）：`db._connect()` 返回 `db._Conn` —— 每条语句都在 `_lock` 内跑完、
并把结果取干净（`db._Result` 持在内存里，接口面刻意收窄）；`_lock` 改 **`RLock`**
（`with _lock:` 块里还会再调 `c.execute`，非重入锁会自锁死）。**169 处调用点一行不改**。
代理绝不能把「还没取完的语句」留到锁外 —— 那正是竞态本身。`db.close()` 也持锁 ⇒ 段错误一并封死。

**变异验证**：把 `_connect()` 退回裸连接 ⇒ 4 例中 **3 例变红**（第 4 例守「锁是重入锁」，本该保持绿），
撤销 ⇒ 4/4 全绿。**集成冒烟**（真 uvicorn + 独立临时根 + 保留 watcher 后台线程）：登录 → 建库 →
写覆写 → **3 读线程 + 1 写线程压 6 秒** ⇒ GET/PUT 出错 **0**、覆写被吃 **0**，服务端日志异常关键字 **0 行**。

### D. 两个坑

1. ⚠️ **`onMounted` 在「登录之前」就跑完了 —— 这是本期唯一一个靠浏览器实测才发现的真 bug。**
   引导最初写在 `App.vue` 的 `onMounted` 里采样一次 `hasNoLibraries`，结果**一次都没弹过**
   （`nf_tour_seen` 始终为空）。根因：**`App` 早在登录之前就挂载好了**（登录是覆盖层 `LoginGate`，
   **不是路由**），那一刻 `loadLibraries()` 拿到 **401**、`librariesLoaded` 仍是 false，
   「0 库」根本不成立；等用户登进来，`onMounted` 早已跑完、不会再跑第二次。
   ⇒ 改成 `watch(() => library.hasNoLibraries, ..., { immediate: true })`：
   无论库是登录后才拉到的、还是用户删掉最后一个库才变成 0 的，都在**成立的那一刻**触发。
   **教训：「等登录后才知道的事」不能用 `onMounted` 采样，必须被动监听。**
2. **`playwright-cli` 用法补三条**（第 37 期记过 `fill` 的坑）：① `--browser=chromium`
   **只对 `open` 有效**，`snapshot` / `click` 带上它一律 `Unknown option: --browser`；
   ② `open` 每次起**新上下文**（localStorage 清空 ⇒ 要重新登录），**同会话里再 `open` 会失败**，
   此后所有命令都报 `browser 'default' is not open` ⇒ 改用 `goto <url>` 做页内跳转；
   ③ 本机默认浏览器是 chrome、**没装**，不开 `--browser=chromium` 直接
   `Chromium distribution 'chrome' is not found`。
   另：`click` 后紧跟 `type` 时第一次 `type` 可能落在**焦点尚未切换**的空档里 ⇒ 重 `click` 一次再 `type`。

### A. 搬迁断链修复（`a1b6d7a`）+ 回滚不搬回关联数据（`a71380f`）—— 都是先修既有真 bug

- `book_id` = `库$sha1(basename)` ⇒ **换库**（库前缀变）与**改名 / 加卷号**（basename 变）都会换 id。
  `REMAP_TABLES` 漏了四张按 `book_id` 存的表 ⇒ 每次移动 / 改名**静默断链**：读点按新 id 查不到，
  不抛异常、不回滚，只无声回落成抓取值或文件原值。
- 修法：`meta_override` / `meta_online` 进 `REMAP_MERGE_TABLES`（**逐行**、同 field 冲突保留目标行；
  整体 `UPDATE` 撞 PK 会被外层 `except` 吞成「搬 0 行」）；`meta_cover` 进 `REMAP_TABLES` 走探测跳过；
  `scrape_items` **另写显式函数**（还带 `library_id` / `source_rel` / `link_rel`），刻意**不进**通用 remap，
  也**不进** `ORPHAN_TABLES`（台账行被删 = 把「磁盘上可能还有个副本」静默遗忘）。
- 回滚此前**只把文件移回原位、不做反向 remap** ⇒ 进度 / 批注 / 改过的元数据永久留在废 id 上。
  按 id 的定义式**重算两侧 id** 再反向搬，不猜、不存快照。

### B. 跨库移动（`70c7f47` 核心 / `d968994` 接口 / `d16bc99` 前端）

- **不另开模块**：与自动归库**共用** manifest / 逐条独立 / remap / 回滚这台机器；判据是「差别只有
  谁选源集合 / 谁定目标库 / 副本怎么处理三处」。`execute` 多一个 `direction` 判别（`DIR_BOOKMOVE`）；
  接口层据此拒收别的方向的批次，**自动归库的字面量 `"move"` 不动**（`migration_last_batch("move")`
  是既有回滚入口，存量批次还躺在 pending 里）。
- **相容闸门判据只有 `library._exts_for_type`**（库扫描白名单的唯一真值源）。不相容**不是半可见**：
  白名单决定扫描认不认，搬过去这本书**从该库书目里直接消失** ⇒ **后端也拦**。`/plan` 才是 400 的落点
  （整批拒绝、不落行），`/preflight` 一律 200（它的职责是把理由列出来）；前端禁选只是体验。
  目录型有声书按 `allow_audio_dir` 同判，不是「没扩展名就放行」。
- **副本随书搬**五情形逐条区分；落点与出版**共用** `publish.relpath_for` + `rel_verdict` + `free_rel`
  ⇒ **预览==落盘靠共用保证**，不是两边各写一遍。落点被外来文件占着则**退让改名，绝不覆盖**。
  `_is_dir_entry` / `_free_rel` 因此改公开名。
- **移动后必须 `watcher.mark_processed(dst)`**：去重键是「相对 `input_dir` 的路径 + (size, mtime)」，
  移进来的文件在它眼里是**全新投递**，不登记会被再入库一次。watcher 按参数注入（同 bookdock）。
- **台账按磁盘实况重量** `link_mode` / `link_shared`（跨卷移动必然换 inode，照抄旧值就是照着旧关系撒谎）。
- 接口五入口**全走 POST**（选择集可能几十本、id 带 `$` 与哈希，query string 迟早撞长度上限）。
  `/apply` **刻意不写 `result`** —— 任务行有 result 就渲染成「下载」按钮，而移动没有产物可下；
  副本计数**按磁盘结果记**（`copied` 而非「打算做什么」）。
- 前端：书架批量条 → **三段式弹窗**（挑库 → 预检 → 确认），**不塞进批量条一键跑完**（真动磁盘）；
  不相容的库**照列 + 写明原因**（抹掉会让用户以为库没建好）；撞名**默认不表态 = 这次不搬这一本**；
  确认文案只报后端数出来的真数字；顶栏「上次移动：甲库 → 乙库 · N 本」+「撤销本次移动」。

**为什么**：`MEMORY.md` 连续两轮被自动注入截断（会话开头即报「too large」）。实测注入上限约 14KB ——
上一轮已压到 15323 字节，仍落在截断点附近，仍会被截。

**做法**（不改规则、只改归属）：`MEMORY.md` **只留每次都必须守的铁律**，把「要动到才查」的域细节
整段外移到 `MEMORY-REF.md`（该文件不参与注入，需要时按指针读）。
- 外移四类：① 环境与构建（`.gitignore` 清单 / macOS 建环境 / `npm install` 的 lock 噪声 / Windows shim）；
  ② 命名与出版细节（`{index}`、`{ext}` 语义、`rel_verdict`、仍改 basename 的两个 `apply_*` 入口）；
  ③ 后端细节（`stats.overview` 键约束、每库可覆盖项清单、可见性判定落点、「两侧查页面入口」）；
  ④ 前端细节（`bridge.css`/`main.css`、图表栈、外观偏好归属边界、侧栏导航契约三则、
  `/explore` vs `/browse` 命名避让、实体总览六维、窄屏写法、`ToolsLayout`）。
  另加一小节「文档锚点核验工具口径」（±6 窗口两难、真值句式误报、同期内先写锚点后改码）。
- 文内保留**指针**（如「可覆盖项清单见 REF」），并逐段压掉叙事性从句（删「为什么 / 后果多严重」，只留规则句）。

**结果**：`MEMORY.md` 15323 → **11157 字节 / 70 行**（−27%，7 段）；`MEMORY-REF.md` 4730 → 10257 字节；
两文件合计 21414 字节。
