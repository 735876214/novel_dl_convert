### 修一：响应 gzip（`server.py` 挂 `GZipMiddleware`）
- 安全性依据（读了 Starlette 源码）：**206 部分响应永不压缩**（音轨/PDF 的 Range 不受影响）、
  `audio/image/video/font/zip` 默认排除、≥128 KiB 走工作线程。
- 体积：`/api/books` **1.36 MB → 491 KB（−64%）**；前端主包 JS **1.02 MB → 301 KB（−70%）**、CSS **121 KB → 20 KB（−84%）**。
- ⚠️ 代价：该端点服务端 **+45–60 ms CPU** ⇒ **LAN 打平、WAN/VPN 显著更快**（两面都记，别只说好话）。

### 修二：并发重复请求 → 单飞闸（本轮最大的一块）
- **根因**：守卫是 `if (loaded) return`，但它在发请求**之前先 `await` 了阈值** ⇒ 让步点，
  同批微任务的调用者全都通过守卫。实测一次页面加载 **`/api/books` 打了 7 次**（2.8 MB、累计 3.6 s）、
  `stats` ×3、`libraries` ×3、`collections` ×2。
- 改 `stores/library.ts`（3 个 loader）、`stores/stats.ts`（**按书库**记在飞）、`stores/collections.ts`。
- ⚠️ **`collections` 的 force 必须「等前一次落地再拉」而不是复用**：`create/remove/rename` 刚改完服务端，
  复用旧的在飞请求会把**刚建的收藏夹吞掉**。
- 实测：`/api/books` **7 → 1**、stats 3 → 1、libraries 3 → 1、collections 2 → 1；整页首次 **≈4 MB → 1.04 MB（54 请求）**。

## 第 68 期 · 收掉第 67 期留下的两处载荷问题（用户点名「这两个优化一下」）

### 一、`/api/books` 不再下发简介正文 → 改发 `has_description`
- **改一处即全局**：`server._card()` 是**所有**书目列表的统一出口（`/api/books`、系列、作者、演播者、收藏夹），
  在里面 `description` → `has_description` 布尔，口径自动一致。
- **实测（600 本）**：原始 **1,363,248 B → 417,189 B（−69%）**；**gzip 后 491 KB → 37 KB**
  （去掉高熵正文后剩余字段重复度极高 ⇒ 压缩率再上一个台阶）。
- **两处消费方**（正是当初判「契约变更」的原因）：
  - `MetadataPage.vue` 缺口筛选：`!b.description` → `!b.has_description`；
  - `BookPreviewDialog.vue` 快速预览：简介改从**它本来就会调的详情**取（浮层原本为章节数调 `GET /api/books/{bid}`）。
- **把 `BookCard.description` 改成可选**是这一步的关键 —— `vue-tsc` 会把所有「还以为列表带正文」的地方一次报出来
  （实测只有上面两处）。这条经验值得复用：**改契约时先让类型变严格**，比人肉 grep 可靠。
- 新增契约 `tests/test_card_payload.py`（2 例）。⚠️ 必须有契约：失效时不报任何错，只有体积悄悄翻三倍。

### 二、`/api/library-migrations/preview`：快 8 倍 + 调用次数减半
- **慢的根因**：`core/migrate.preview()` 对**每本书**都调一次 `libraries_of_type()`（读库表 + 组装列表）；
  600 本实测仅这一项 ~200 ms（端点 ~300 ms）。改为**循环外算一次**「类型→同类库」「id→库」映射 + 目标库根按库缓存。
  抽 `_pick_from(dsts, …)`，`_pick_dst` 留作便捷包装。**~300 ms → 37 ms**（`test_migrate.py` 全过，口径未变）。
- **被调 2 次的根因**：`App.vue` 的 `<MigrationGateDialog v-if="!showLogin">` 而 `showLogin` 初值 `false` ⇒
  未登录时**先挂载→鉴权失败卸载→登录后再挂载**。
- ⚠️ **坑：用 `auth.ready` 当门不够** —— 它在 `auth.init()` **内部**先变真，而 `showLogin` 要等 `await init()` 回到
  App.vue 才赋值；中间那个 tick 里 `ready=true && showLogin=false`，照样多挂一次（实测第一次改完仍是 2 次）。
  正解是 App 自己的 `authChecked`（两件事都定好才置真）。**2 次 → 1 次**。

- 后端全量 **1182 / 0 failed / 0 error**（+ 新契约 2 例）；前端 `type-check` 0 错 + `test:unit` **340** + `build` + `deploy` 全绿。
- 真机（600 本 + 隔离实例 + Edge）：preview 只 1 次、`/api/books` 只 1 次真实拉取（gzip 38 KB）。

### 第 72 期：TXT 阅读全乱码 —— 编码探测「样本截断」+ 长章书分章退化

**缘起**：用户报「收书目录导入的那本书阅读时已经全部乱码」，详情页显示 **3723 章**。
先排除导入链路（`pipeline.dispatch` 只 `shutil.copy2`，源与库副本 md5 逐字节相同，
文件本身是**合法 UTF-8**：1,111,029 B / 373,187 字符）—— 真因是**三处判据**，
且**只修编码不够**：编码修对后同一本书仍是「3723 个中文标题 + 零正文」（实测）。

**缺陷 A —— 按字节切出来的样本被当成了「这不是 UTF-8」的证据**（`core/pipeline.py`）。
`_sample_bytes` 按**字节**截头 256 KiB，切点有 2/3 概率落在 3 字节汉字中间（本书正切在
262142-262143，`e6 b7` 是某 3 字节字符的前两字节）；老实现 `decode("utf-8-sig")` 是**严格**
自证 ⇒ 尾部不完整即抛 ⇒ 落进 gb18030/big5 打分（utf-8 不在候选里）⇒ 判 gb18030（打分
+0.4702 胜出，正确 utf-8 是 +1.9375）⇒ 全文乱码且**全程不报错**（调用方还叠加
`errors="ignore"`）。**判「前缀」的唯一写法**：`codecs.getincrementaldecoder("utf-8")().
decode(data, final=False)`（每次新建实例，解码器有状态）——只容忍**尾部**不足一个字符，
**中间**坏字节照旧抛（实测真 GBK/Big5 仍判 False）。新增 `ENCODING_RULE_VERSION = 1`。

**缺陷 A2 —— 两段样本拼接，接缝处自己造了个假非法字节**（同族第三处，本用例先红才补的）。
「开头纯 ASCII」时补采中段，起点 `size // 2` 按字节算、多半落在字符中间 ⇒ `data + more`
在**中间**放了个续字节（`0x80–0xBF` 不能当字符开头），前缀判定只容忍尾部 ⇒ **救不了它**，
真 UTF-8 书照样被判 big5。修法 `_read_from_char_boundary`：① 窗口内先找换行（`0x0A` 在
UTF-8/GBK/Big5 里都不可能做后继字节）；② 没换行就跳过开头续字节。头部全 ASCII ⇒ 尾部
必是边界 ⇒ **只需对齐中段起点**。

**缺陷 B —— 长章不是「命中太少」**（`core/detect.py`）。老闸门 `len(bounds) * 2000 >=
len(text)`：25 章 × 2000 = 50,000 < 373,187 ⇒ 判「正则无效」⇒ 退化缩进切分 ⇒ **3723 章 /
0 字正文**。`CHAPTER_RULE_VERSION` **2 → 3**，三处口径变化：① 新公开函数
`regex_confident(bounds, text)` = 密度 **或** 条数 ≥3（行首锚定后 3 条以上基本不是巧合）；
② **降级产物一章正文都没有 ⇒ 回退正则边界**；③ `_split_by_indent` 认**全角空格**
（本书 3697 行用 `　　` 缩进、只 26 行顶格；必须与 `_LEAD` 的字符集一致）。
⚠️ **同一判据不许第二份拷贝**：`ai_detect.HybridChapterDetector` 里那份已收敛；
`mode: regex` 直接委派 `detect_chapters`（老写法少写保险 ⇒ 同文本走管线与走检测器得到
**不同目录**）。**行为变更**：hybrid 下长章书不再触发 LLM（此前一本已切对的书每次都花钱）。

**缓存指纹**：能改正文产出的口径都得进指纹。第 62 期只放了分章规则版本，本期补
`txtcache.ENC_RULE_VERSION`（跟随 `pipeline.ENCODING_RULE_VERSION`）→ `state.json` 的
`enc_rule` + `_SPLIT_CACHE` 键 + `server` 原生路 Redis `extra`（`v3:e1`）。
