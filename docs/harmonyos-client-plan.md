## 1. 需求来源

用户三次收敛后的原话意图：

1. 「评估将本项目同步开发鸿蒙端的可行性」—— 要结论，不要先把代码写出来。
2. 「我想要有原生体验的 App，但是侧载安装就行」—— 排除纯套壳、排除上架路线（免备案/软著/审核）。
3. 「鸿蒙端仅用作前端阅读器，书籍内容、阅读进度等保存在 nas 里」—— 纯瘦客户端，端内不落业务数据。

由这三条推出的**锁定项**（不再讨论）：

| # | 锁定 | 依据 |
|---|---|---|
| L1 | 端 = **阅读消费端**：只读 + 写进度/批注/偏好 | 判据一条不新增（AGENTS §1 单一真值源） |
| L2 | **纯瘦客户端**：端内只有 `baseUrl` / `token` / `deviceId` 三个持久值 | 断网即不可用，须如实报错 |
| L3 | **仅局域网**直连 `http://<NAS-IP>:8992` | 免多地址/VPN/穿透 |
| L4 | **R1 路线**：登录/书架/详情用原生 ArkTS，**阅读面用 ArkWeb 载入现有 SPA** | `views/ReaderView.vue` 141KB 交互不重写 = 不产生第二份实现 |
| L5 | **侧载分发**（`hdc install`），不进应用市场 | 免审核链 |
| L6 | 位置换算/阅读阈值/续接/编号**全部消费服务端**，客户端一行判据都不写 | `core/epub_cfi.py` 等是唯一真值源 |

**外部前提（本仓库无法验证，M0 交付物）**：`Web` 组件 / `WebviewController` 的 JS 注入 API、`module.json5` 明文 HTTP 开关键名、
调试签名有效期、`hdc install` 参数 —— 均属外部 SDK 事实，该环境 `web_search` 亦不可用。排期把这些当**核实任务**，不当已知条件。

## 2. 功能范围

### 2.1 一句话边界

> 鸿蒙端 = 阅读消费端。管理类 300+ 路由不进原生端；需要时**单点**用 WebView 打开 `/static/v2`，不写第二套原生页面。

### 2.2 六个页面

| 页面 | 依赖接口 | 备注 |
|---|---|---|
| 登录 | `GET /health`（预检，免鉴权）、`POST /api/auth/login` → `{token,user}` | 不做注册/找回 |
| 书架 | `GET /api/books?limit&offset`、`GET /api/libraries` | **不做库切换**（见 §5 第 1 轮 F3） |
| 详情 | `GET /api/books/{bid}`（`chapters` 按卷分组，叶子 `index` 即章节入参） | 编号只显示服务端 `title` |
| 阅读容器 | ArkWeb → `{baseUrl}/static/v2/index.html#/read/{bid}?chapter={index}` | SPA 侧负责翻页/版式/批注/听书 |
| 设置 | `GET/PUT /api/prefs/devices/{did}` | 整体替换语义，读-改-写 |
| 关于 | `GET /health` | 唯一给版本号的端点 |

### 2.3 不做清单（写死，防范围蔓延）

多服务器地址 · 离线缓存/下载 · 注册与找回 · **库切换（书库维度筛选）** · 管理端原生化 · 自动更新通道 · 应用市场发布 ·
多用户 · 客户端 CFI · 客户端阅读阈值/续接推算 · **客户端自算阅读状态角标** · 假数据演示模式。

## 3. 防回归要点

### 3.1 接口契约只有一处真值源

`tests/test_client_contract.py`（**13 例**）是端上类型的唯一依据。**端上 `types.ets` 只能照它写**，
字段增删改必须先改契约测试。三条判据：顶层键集合精确相等（服务端自组装响应）／必需子集 + 禁 `path`
（按行透传的卡片、批注、设备档案）／**字段面快照**（八组端点压成键路径集合，多一个少一个都红，
重写要 `NF_CLIENT_SURFACE_WRITE=1` 并人眼 diff）。已钉死的关键形状：`/api/books` 六键壳（`has_more` 驱动分页）、
卡片无 `path`/`description`、详情 `chapters` 按卷分组、进度 `file_rel` 可为 `null`、会话带 `session_uid` 即 upsert、
批注 `start_off` 缺省 `-1`、偏好 PUT 整体替换且 `active_profile_id` 不传即保留。

### 3.2 不许在端上重造前端已有的判据（本轮审查的主要教训）

| 判据 | Web 端已有实现 | 端上正确做法 |
|---|---|---|
| 书内 CSS 是否生效 | `ReaderView.vue:332` `scopeSupported()` 探测，不支持则**不注入**、回落应用排版（`:369`） | 什么都不做。**不要**在原生侧再造降级分支 |
| 设备 id 生成 | `lib/deviceInfo.ts:31` 已有 `randomUUID` 兜底 | 端上用 ArkTS 生成一次即可，不引 `crypto` 兼容层 |
| 章节/批注编号 | `lib/annotations.ts:14` `chapterLabel = 第 (chapter+1) 章`（前端 TS，ArkTS 调不到） | **不显示编号**，只显示服务端返回的 `title`；不自造 `+1` |
| 阅读状态角标 | `stores/library.ts:243` `statusFromPercent(percent, thresholdsFor(lib))`，阈值来自 `GET /api/reading-thresholds?library_id=` | 只显示服务端 `status` 字段；为 `None` 时**不显示角标**（不猜） |
| 会话来源 | `db.py:2039` `SESSION_SOURCES = ("web","audio","manual")` | 复用 SPA ⇒ 一律记 `web`，端上**不自报** `source`（自报非枚举值必 400） |

### 3.A 版本协商：`/health.version` 是端上唯一的版本判据

**为什么侧载端比 Web 端更需要它**：Web 端刷新即拿新 bundle，前后端永远同版本；侧载 App 停在用户装的那个
HAP 上，**没有自动更新通道**，后端升级后它可能面对一个字段已改的 `/api/*`。表现不是崩溃，而是「书架空白」
「详情少字段」这类**看起来像 bug 的静默降级**。

判据只有一条，且不需要新增后端接口：

- `GET /health`（**免鉴权**，中间件只拦 `/api` 前缀，`server.py:445`；登录页就能问）返回
  `{status, checks, problems, input, output, watcher, version, updater_available, logs}`，
  其中 `version` = `server.APP_VERSION` = 仓库根 `VERSION`（唯一真值源）。
- 端上硬编码 `MIN_SERVER_VERSION`：`server.version < MIN_SERVER_VERSION` ⇒ 拦住并提示「服务端过旧，请先升级 NAS 端」；
  比它新则不拦（端上忽略未知字段）。
- 这条规则本身也被测试钉住了：`test_version_is_single_source` 断言 `VERSION` 文件 == `/health.version`
  == openapi `info.version` ⇒ 谁再写第二份版本字面量，测试先红。

⚠️ **不要**把 `/openapi.json` 当契约来源：实测 292 条 path 里，`/api/auth/login`、`/api/books`、
`/api/prefs/devices/{device_id}`、`/health` 的**响应 schema 全是 `{}`**（端点直接返回裸 dict、没有 `response_model`），
且路径参数名是 `{bid}` 而不是 `{book_id}`。拿它当契约会得到一个「看起来有门禁、实际什么都没钉」的假门禁 ——
这正是本文件把 A 方案落地成「真实调用 + 键路径快照」的原因。

### 3.B 决策记录：**不做前后端物理分离**（改做契约门禁）

用户提出「为确保后端改动不影响网页端与鸿蒙端，考虑前后端分离」。评估结论：**这个项目在协议层已经是分离的**，
真正缺的是**门禁**；物理拆分不解决「字段悄悄改名」，反而新增「前端/端上版本与后端错配」这个现在不存在的风险。
实测的分离代价（逐条都可复发）：

1. 服务端只挂了 `GZipMiddleware`（`server.py:301`），**没有 CORS** ⇒ 拆域必须新增 CORS 且要配 `allow_*` 与预检；
2. SPA 资产是**绝对路径** `/static/v2/assets/...`（`novelforge/static/v2/index.html:36-39`）⇒ 拆域要改
   `VITE_BASE`（`frontend/vite.config.ts:13,20`）重新构建并改部署脚本；
3. 前端 4000+ 行全是相对 `/api/...`，无 `API_BASE` 概念，开发期靠 Vite proxy（`vite.config.ts:44-49`）⇒ 要引一层环境配置；
4. 封面/音频/字体靠 `<img src="...?token=">` 的**同源**语义（`_MEDIA_TOKEN_PATHS`）⇒ 跨域会污染 canvas（漫画/PDF 渲染）；
5. AGENTS §1 只许两份 compose、禁新增叠加件 ⇒ 「前端容器 + 后端容器」这种标准分离形态在本仓不被允许；
6. 静态 SPA 直接从磁盘发（`server.py:313`），改前端不必重启后端 —— **已经**获得了分离最主要的那个好处。

因此本轮落地的是 A + B：A = `tests/test_client_contract.py` 的字段面快照（少/多字段都红），
B = 上面的 3.A 版本协商。若将来真要物理拆分，先满足一个前提：**单一网络入口纪律** ——
前端裸 `fetch(` 只剩 6 处（`frontend/src/lib/api.ts:3060/3741/3767/3860`、
`components/book/detail/TocSourceCard.vue:63`、`views/settings/pages/MetadataPage.vue:256`），
先全部收敛到一个 `request()` 出口，才有「换 base URL」的落点。
